The problem

Post-quantum deadlines are hitting device fleets that were never built to change their root of trust

2030NSA CNSA 2.0

Software & firmware signing: CNSA 2.0 only

"Begin transitioning immediately, support and prefer by 2025, exclusively use by 2030." Firmware signing has the earliest deadline in the suite.[1]

2027EU CRA

Cyber Resilience Act fully applies on 11 Dec 2027

Products must be maintainable with security updates. Vulnerability reporting has applied since 11 Sep 2026.[2]

2035NIST IR 8547

ECDSA and RSA signatures disallowed after 2035

The 112-bit variants are deprecated after 2030 (initial public draft).[3]

39 BIoT, 2030

21.1 B connected devices in 2025 → 39 B by 2030

Connected products often stay in service for 10–20 years. Their bootloader keys were chosen long before PQC.[4][5]

04
The agentic loop

The AI proposes, the emulator measures, the engine decides, and a human chooses the next step

AMD-hosted AI

① Plan tests

Picks and orders the optional registered checks. Required checks always run, and unknown templates are blocked and shown.

Runner

② Execute for real

Pinned build, ephemeral keys, Renode boot and update, UART capture. No network access, and every artifact is hashed.

V1.2 engine

③ Deterministic verdict

Candidate, transition and migration verdicts plus an explanation graph and a canonical hash. Golden-hash regression tests guard it.

AMD-hosted AI

④ Explain + alternatives

Explanations must cite real evidence IDs. Alternatives come only from the profile's allowed set and are labelled PROPOSAL.

Human + engine

⑤ Re-evaluate

A human picks an alternative. That creates a new run with a parent reference, and history is never changed.

↺ the re-evaluation feeds back into ③ or, when new tests are needed, starts a new LIVE run at ②

Evaluation

One business result, one failure case, one limitation and one human safeguard

Business result · measured

A blocker that boot-only testing misses, found in under a minute and backed by evidence

wolfBoot: the ML-DSA-87 candidate boots (a boot-only check would report PASS), but deployed devices cannot get there. The engine shows this with cited evidence before any device is touched.

Run a39610. MCUboot run 7682fc: 75 s, 7/7 tests, 50 artifacts. Manual-effort savings are not claimed as measured.

Failure case · observed

Runner killed mid-run ⇒ FAILED, and no verdict is issued

Run RP-20261017T124942Z-23dd8f: /result returns 409 and there is no fallback to recorded data. Our own acceptance gate also failed a wolfBoot run when Renode tried to download its SVD on the no-egress network. E01 was reported INCONCLUSIVE instead of being faked, and we fixed it by baking in and pinning the SVD.

Known limitation

This is emulation, not silicon, and only two configurations are supported

  • Renode models nRF52840 flash as plain memory (wolfBoot), and our NVMC model for MCUboot is minimal, so there are no power-loss or timing faults.
  • Interrupted-update recovery (E12) is not executed, so INV-I4 stays UNKNOWN.
  • Verdicts are non-official engineering assessments, not certifications.
  • Early screenshots used deterministic fallback; later AMD-required acceptance and Token Factory smoke are retained separately.
Safeguard · human review

The AI never changes a verdict. An engineer chooses and signs off

  • AI output is labelled PROPOSAL, and choosing an alternative creates a new run.
  • Alternatives marked REQUIRES_EXTERNAL_VALIDATION are refused (HTTP 422).
  • Every result carries the engine version, canonical hash and manifest of inputs, pins and artifact hashes, so a reviewer can trace each claim.
  • The "Ask about this run" assistant only produces text from the run's evidence. It has no tools and cannot start runs.

Our wedge

The cross-generation test (X01) puts the deployed bootloader in front of the candidate's image. Combined with field-update capability and negative tests, it answers the question a CBOM or per-algorithm CI cannot: can this fleet actually get there?

Complementary, not a replacement

A CBOM tells you what to migrate, an OTA platform delivers the update, and ReleaseProof tells you whether the path works before you ship. They are integration partners as much as competitors.
